# Lab (teacher guidance + on-site guided lab/workshop + rubric)

> **Bootstrap:** if you start from zero: (1) locate the course root — the nearest ancestor
> folder containing `.claude/refs/course.yaml`; (2) read `course.yaml` (language, folder
> names, enabled artifacts, tool stack, publishing targets); (3) read
> `.claude/refs/PROTOCOL.md` — the course's contract; (4) read your session handover
> `.claude/refs/handovers/handover-S<NN>.md` if it exists; (5) read
> `.claude/refs/shared-context.md`. If `lab` is not in `artifacts.enabled`, STOP and warn
> the conductor. Write ALL generated content in `course.language`.

**Tier:** Sonnet (writes the guidance script and the guide) · Opus if the tool/build or topic
calibration is delicate · Opus (you orchestrate and judge) · Haiku/Bash (materializes the
rubric by running `generate_rubric.py`).

## What you produce

In the `<folders.labs>/` folder (default `labs/`, per `course.yaml naming.folders`):

1. **`<folders.labs>/S<NN>-lab-guidance.md`** — the teacher-guidance script that OPENS the lab
   block: the lab's core concepts in beats + at least one **runnable live demo** of the
   pattern/topic the groups are about to build or work through. **Instructor-only — never
   published** (same convention as any instructor-only pack the course keeps unpublished).
2. **`<folders.labs>/S<NN>-lab.md`** — a **written, self-paced, step-by-step guide** for groups
   (group size per the course's convention in PROTOCOL.md, typically 2–3), run right after the
   guidance, with the **rubric embedded as a Markdown table** at the end.
3. **`<folders.labs>/S<NN>-rubric.json`** — the rubric source (additive criteria + `penalties`).
4. **`<folders.labs>/S<NN>-rubric.xlsx`** — the rubric for grading (generated by
   `generate_rubric.py`).

## Lab conventions

- **Groups per the course's stated size** (typically 2–3 students), one deliverable per group
  with a **cover page** (names + student IDs of the group) — format and medium per the session
  plan / PROTOCOL.md (e.g. a PDF group report).
- **Teacher guidance first, then the self-paced guide:** the instructor opens the lab block
  with the core concepts + a **live demo** (from the guidance script); groups then follow the
  written guide end-to-end **on their own**. The guidance motivates and demos the pattern/topic
  — it must **not** duplicate the guide's numbered steps. Durations for each block (guidance vs.
  work time) come from the session plan / PROTOCOL.md's session shape for this session type.
- **Every numbered step yields a verifiable deliverable** — a file, a screenshot, a running
  result, a committed change, a bitácora entry. **No step is purely organizational/logistical**
  (no roll-taking, no "introduce yourselves", no "agree on roles" step that leaves no evidence
  and maps to no rubric criterion): fold any logistics into a real step that produces something.
- **NO clock, NO timeline, NO per-step minutes, and NO prescribed "break" block in the guide.**
  This is a firm rule (the no-timeline-in-labs rule): a lab is an **ordered list of steps**
  (Step 0, Step 1, Step 2, …), not a chronometer. Any timing (guidance slot, work slot, breaks)
  lives in the session plan and PROTOCOL.md — **never** inside the lab guide itself. *(The
  guidance SCRIPT may carry rough per-beat minutes for the instructor — it is a teaching script,
  not a student guide, so this rule does not apply to it.)*
- Each step names the exact action, what the group should see, and a **verification point** ("if
  you don't see X, check Y"). Plain language for the course's audience (per its glossary), no
  unexplained jargon.

## Inputs (read, don't duplicate)

- The session plan (`<folders.planning>/S<NN>-plan.md`) — the plan's lab/workshop spec
  (objective + the transferable pattern or topic to build/cover, and whether this session is a
  workshop per §Workshop mode below).
- `sources.session_briefs` → the session's lab/workshop description and its grading-category
  notes.
- `sources.glossary` — shared vocabulary for the course's audience.
- `.claude/refs/grading-penalties.md` — the standard penalties block (single source; injected).
- Any prior-year reference material the course PROTOCOL points to for this artifact (open it via
  the handover's source-pointer table before writing, if the course keeps one) — evaluate and
  keep what serves; never copy wholesale.

## Process

1. **Confirm the build/topic** from the plan's lab spec (objective, tool or pattern, and whether
   the tool/flow is still current — if in doubt, mark pending for the conductor rather than
   inventing UI steps you haven't verified).
2. **Author the teacher-guidance script** (`S<NN>-lab-guidance.md`; Sonnet writes, Opus judges)
   — structured in **beats with rough minutes** (this file is for the instructor, so minutes ARE
   allowed here): the lab's core concepts explained for the course's audience, plus at least one
   **runnable live demo** (goal · setup · steps · expected result · **live-failure fallback**).
   It previews and motivates what the groups will build; it does **not** walk the guide's
   numbered steps.
3. **Author the ordered steps** (Sonnet writes; ↑Opus if the tool/build is delicate). Structure:
   - **Objective** and **expected result** (what the group ends up with).
   - **Prerequisites** (accounts, repo, tooling already set up from earlier sessions).
   - **Step 0, Step 1, Step 2, …** — an ordered list, **no minutes on any step**. Each step:
     exact action → what you should see → **verification point** → the **deliverable it
     produces**.
   - **Deliverable:** per the session plan's format (e.g. a group report with a cover page).
4. **Build the rubric** (engine `evaluation-rubrics:rubric-creator`). **You author the JSON**,
   then run the plugin's script:
   - Criteria mapped to the lab's key deliverables/steps — broad, additive, no "holistic"
     filler, and **never one criterion per lab step** (group steps into a few gradeable
     clusters); three descriptor levels (Meets / Partially meets / Does not meet), formal
     register, criterion names 3–6 words. Follow the rubric plugin's descriptor-writing rules in
     `$(dirname "$RC")/../references/performance-levels.md` (resolved from the located
     `generate_rubric.py`).
   - **Weights MUST sum to 100** (hard assert in `generate_rubric.py`). This artifact's point
     value inside the course's `evaluation.weights` is applied separately in the gradebook —
     not here.
   - **Standard penalties (ALWAYS) — passed as `penalties`, NOT additive criteria.** Copy the
     rows from `.claude/refs/grading-penalties.md` into the JSON `penalties` field verbatim (do
     not reinvent them). When invoking the plugin, say so explicitly: these rows are penalties,
     not additive criteria (they render as a separate labeled block outside the additive 100, so
     they don't break the `sum==100` assert).
   - **Materialize:** write `S<NN>-rubric.json` with schema `{language: course.language,
     criteria:[{name,cumple,parcial,no_cumple,pts}], penalties:[{name,cumple,parcial,no_cumple,penalty}]}`.
     ⚠️ The descriptor keys are **literally `cumple` / `parcial` / `no_cumple`** regardless of
     language — `generate_rubric.py` reads those exact keys; `language` only switches the
     rendered column headers. Then run:
     ```bash
     RC=$(find "$HOME"/.claude*/plugins -path "*rubric-creator/scripts/generate_rubric.py" 2>/dev/null | sort -V | tail -1)
     python "$RC" S<NN>-rubric.json S<NN>-rubric.xlsx
     ```
     *(Locate the script scoped to `~/.claude*/plugins` — never `find /`; if multiple versions,
     use the highest. Requires `openpyxl`. The plugin's "Review in Chat" step does not apply
     here — the conductor's md-first gate IS the approval.)*
   - **If the script fails** (`openpyxl` missing → `pip install openpyxl`; weights ≠ 100 → fix
     and retry; script not found), alert the conductor and leave the `.md` with both tables
     ready.
5. **Embed the rubric in the `.md`.** At the end of `S<NN>-lab.md` put two tables: (a) the
   additive rubric (Criterion · Meets · Partially meets · Does not meet · Pts, summing to 100)
   and (b) the penalties block ("scored negatively"). `generate_rubric.py` writes both into the
   `.xlsx` in one step.
6. **Judge (Opus):** mentally execute the steps in order — verify no jumps, no "and then
   configure it", correct build/topic for the session; run the guidance script's demo mentally
   (does it produce the expected result? is the failure fallback real?) and check it doesn't
   duplicate the guide; audit the rubric against the acceptance criteria; if this is a workshop
   session, also audit against §Workshop mode below.

## Workshop mode

> Applies only when the session plan / course PROTOCOL marks this session as a **workshop**
> (an in-person session reusing this skill instead of a plain lab) — a config/plan-gated
> variant, not a separate skill. Everything else in this skill is reused as-is (rubric engine,
> standard penalties, publication via the publish engine, no chronometer in the guide, group
> cover page); this section states only what changes.

- **Deliverable = a log/bitácora-style product, not a "lab report."** The group documents its
  work case-by-case in a log-type product (e.g., for a topic like prompting, a prompt library).
  Still delivered with a group cover page (names + IDs; drop anyone who didn't contribute).
- **The guide is the didactic progression of the topic, not a tool walkthrough.** The numbered
  "steps" are the topic's own steps (e.g. building something layer by layer), each with its
  action, verification point, and corresponding log entry. The "no purely organizational step"
  and "no chronometer" rules still apply.
- **Groups and cases:** group composition and any case assignment (e.g. random case assignment
  by the conductor) follow the course's stated workshop convention in PROTOCOL.md — do not
  invent a case-assignment rule; ask the conductor if the plan doesn't specify one.
- **A group-presentation criterion is required.** Workshops typically span two meetings: one
  for the topic exposition (produced separately by the slides skill) plus work time, and a
  second where each group presents one of its cases. This does not produce a new slide
  artifact — the workshop guide describes what gets presented and how — but **the presentation
  counts toward the grade** and must appear as its own rubric criterion.
- **Rubric aligned to the topic's conceptual axes, not to each mechanical step.** Derive
  criteria from the topic's core axes plus product/log quality plus the group presentation —
  broad criteria, not one per progression step. Same standard penalties apply.

## Acceptance criteria

- [ ] `S<NN>-lab-guidance.md` exists — a teacher script in beats with rough minutes: core
      concepts + ≥1 runnable live demo (goal · setup · steps · expected · live-failure
      fallback), previewing the pattern/topic without duplicating the guide's steps.
      Instructor-only.
- [ ] Someone unfamiliar with the material could follow the guide without help, end to end
      (after the guidance).
- [ ] Every numbered step yields a verifiable deliverable; no purely organizational/logistical
      step.
- [ ] NO clock anywhere in the guide — no timeline, no per-step minutes, no prescribed break
      block. Steps are an ordered list.
- [ ] Group size and deliverable format match the course's convention (PROTOCOL.md / session
      plan); cover page present.
- [ ] Correct build/topic for the session, per the plan.
- [ ] Rubric generated (`S<NN>-rubric.json` + `.xlsx`): broad additive criteria mapped to key
      deliverables/steps, weights sum to 100.
- [ ] Standard penalties block present, copied from `.claude/refs/grading-penalties.md`, passed
      as `penalties` (not additive), rendered as a separate "scored negatively" table.
- [ ] Both the additive rubric and the penalties block appear as tables at the end of the `.md`.
- [ ] **If workshop mode applies:** deliverable is a log/bitácora product (not "lab report");
      rubric includes a group-presentation criterion; rubric is aligned to conceptual axes, not
      mechanical steps.

## Publication (this skill owns its pipeline end-to-end)

After the **human validates** the `.md`:

1. **Publish the guide** `S<NN>-lab.md` → Google Doc via the `publish-google-doc` engine (into
   the labs Drive subfolder per `publishing.drive.subfolders`). Record the link in the handover.
2. **The guidance script is NOT published** — `S<NN>-lab-guidance.md` is instructor-only (it
   rides Drive folder sync as a plain file).
3. **Rubric `.xlsx`:** it already reaches Drive via folder sync — do NOT re-upload it through
   the connector (that creates a duplicate). It is a file for the instructor, not a Google Doc;
   the `.json` stays as the editable source.

## Close

1. Write the files (guidance script + guide + rubric `.json`/`.xlsx`) and self-audit against the
   acceptance criteria.
2. **Human gate (md-first):** the conductor validates the guide. *(End the turn with a summary;
   do not publish until the green light.)*
3. **Publish** the guide to a Google Doc; the `.xlsx` rides Drive sync (see §Publication).
4. **Update the handover** (check the lab box; note whether the rubric generated or is pending,
   and the Doc link), **add lessons** to `shared-context.md` (tier calibration, traps), and
   **record decisions** in `<folders.sources>/<sources.decisions>` if any were made, and **emit
   the closing block** per `templates/next-agent-prompt.md`: a human summary, then the PROMPT
   FOR THE NEXT AGENT — the next artifact slug comes from the course PROTOCOL's artifact
   sequence for this session type (do not hardcode a specific next slug).
